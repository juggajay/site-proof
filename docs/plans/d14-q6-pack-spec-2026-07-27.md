### 0.3 Rev 2 changelog — refutations

1. **The pavement research's §6.3 gap 1 — "`QuantityUnit` has no tonnes and no linear metres" — is false.** `backend/src/lib/readiness/sufficiency/types.ts:37` ships `QUANTITY_UNITS = ['m2', 'm3', 't', 'm', 'each']`, and `frontend/src/lib/testSufficiency.ts:33-39` already renders all five. The research's rules #8, #11, #13 and #14 are **not** blocked on a vocabulary addition. They are blocked on something else, which §4.6 and §5.6.3 name: a lot records **one** quantity in **one** unit, so an areal pavement lot cannot also supply the tonnage a binder rule counts against. Recorded as a scope item, not a type change.
2. **The pavement research's §4.2 option 2 — a separate `tfnsw-q6-pavement.v1` ruleset — is not implementable and must not be built.** It assumes "resolution keys on `activitySlug`". `resolveRuleset` (`registry.ts:46-66`) selects exactly **one** ruleset per `(state, specSet, date window)`, newest `effectiveFrom` wins with `id` as tie-break. Two live NSW/TfNSW packs would **shadow** each other, silently deleting either the earthworks or the pavement rules from every NSW project — the under-testing direction, arriving quietly. §5.6.2 takes a third route the research did not consider. Its rejection of option 1 (`defaultScale`) is correct and is adopted.
3. **The pavement research's §7 limit-3 pin example is half wrong.** *"a 3,000 m² Class 1 DGB subbase lot requires 5 tests"* — the `> 100.0` row's `> 1,000, ≤ 5,000 m²` cell publishes *1 per 500 m² (min 5)*, so 3,000 m² requires `max(5, ceil(3000/500)) =` **6**. The second half ("a 6,000 m² one requires 10, not 6") is correct. AT-55 pins the **corrected** pair. Recorded in the research doc's provenance header too.

*(Review item `[D14R-R6]`'s "eight rate-bearing cells" is corrected to nine in §0.0.2 rather than listed here — the recommendation itself holds.)*

## 1. Outcome, scope and non-goals

**Outcome.** An NSW earthworks lot gets a real, spec-cited required test count instead of silence; a VicRoads Type A lot that is too big gets warned and a Type B lot of the same size does not; and a VIC lot under 500 m² is told, in the authority's own numbers, about the cheaper testing route the specification actually gives it.

**Included:**

- **One new lot attribute** — `Lot.materialType` (§3.1), nullable, additive, entered on the lot form, the bulk-set route, bulk create and PATCH.
- **A decision that the second attribute is not needed** — the specified relative compaction band rides the shipped `Lot.testScale` slot (§3.2). The rejected alternative and its flip condition are recorded.
- **A third attribute, specified and now DEFERRED by Jay** — `Lot.smallAreaElected` (§3.3), the Section 173 election. **J3 resolved: advisory only; the election tick-box (phase D14.4) waits for a pilot to ask** (§16.0). The advisory needs no schema at all and ships in D14.2.
- **Five optional rule-vocabulary fields** (§4): `LotSizeCap.materialAliases`, `Ruleset.materialTypes`, `Ruleset.scaleLabel`, `FrequencyRule.countByAreaBand`, `FrequencyRule.smallLot` — and one optional-ification of `FrequencyRule.minCountByScale`. Plus one resolution field, `ResolvedSufficiency.geometryAreaM2` (§4.6), which is not vocabulary.
- **`tfnsw-q6.v1`** (§5) — TfNSW Q6 Table Q6/L.1 encoded in full, all 25 cells, at `status: 'confirmed'`, with `tfnsw-r44.v1` deleted.
- **The `vicroads-204` upgrade** (§6) — the Type-A-scoped 5,000 m² cap `[C1C-3]`, and the Section 173 small-area limb shipping **advisory-first**.
- **The Q6 pavement extension** (§5.6, phase **D14.5**) — the J4 research pass came back grade A and **approved**: Q6 cl. 3.8.3 makes Annexure Q6/L own pavement sampling frequency, so pavements are **rules inside the pack that already ships**, not a new table and not a new pack. Nine of the research's eighteen rules are encodable with nothing new.

**Non-goals — explicitly not built here:**

- **No statistical acceptance.** Not the Q6 characteristic value `Q_L = x̄ − ks`, not the Section 173 mean-vs-characteristic switch, not the +2.0 % threshold comparison. C1 counts tests; it does not evaluate result **values** (C1 spec §1, §16 D8). §6.3 states the mitigation for the one place this can mislead.
- **No new UnknownCause, no new reason code.** Both vocabularies are closed and contract-tested (`contracts/reasonCodes.ts:24-28`, `:74-78`); this slice reuses them (§4.5).
- **No lot-sampling-interval limb.** VicRoads Table 204.142's "every 2nd/3rd/6th lot" stays inexpressible and unencoded `[C1C-5]`. The warning against encoding `{A:2,B:2,C:6}` as counts stands.
- **No spatial, no per-production-day, no duplicate-sample detection, no LIMS.** C2/C3/C4 as per the C1 spec.
- **No new page, no new panel, no shell file.** Three form controls at most, on office surfaces.
- **No second NSW ruleset.** `resolveRuleset` (`registry.ts:46-66`) returns exactly **one** pack per `(state, specSet, date window)`, so a second live NSW/TfNSW pack would **shadow** the first. The pavement research's §4.2 option 2 is refuted on that ground (§0.3 item 2) and must not be built.
- **No per-lot multi-quantity model.** §4.6 resolves a quantity **per required unit** from what the lot already holds; it does not let a lot record both an area and a tonnage. That gap is what keeps the research's tonnage- and chainage-keyed pavement rules out of scope (§5.6.3), and it is named, not closed.
- **No Q6 reduced-frequency limb, pavements included.** Q6 cl. 3.8.3 *does* publish one (up to 50 % by proposal) — the earthworks report was wrong to record it as absent — but it is Principal-approved and revocable, so nothing in a lot record can establish it. §5.6.4 specifies the deferral and its reason.
- **No `pavement_concrete` scope.** The pass read R71, R73 and R75; no concrete-pavement or foamed-bitumen (R76) specification was obtained (§5.6.3).

## 3. The D14 lot attributes

### 3.1 `Lot.materialType` — the material class, authority-scoped values

```prisma
// D14: the authority's material classification for this lot — VicRoads/DTP
// Type A / Type B / Type C, and whatever a future authority calls its classes.
// FREE TEXT like `layer` and `areaZone`, NOT an enum: 'Type A' is VicRoads
// vocabulary and a TfNSW or TMR pack would classify differently. The PACK
// declares which strings it recognises (`Ruleset.materialTypes`, §4.2) and the
// route validates against them, so the column generalises while the values stay
// authority-scoped. NULL = not recorded (§3.4).
materialType String? @map("material_type")
```

**Decision: the slot generalises, the vocabulary does not.** Every road authority classifies earthworks material somehow; none of them agree on the labels. An enum of `A | B | C` would be VicRoads' vocabulary frozen into the schema and would be wrong the first time a second authority needs it. A free-text column matched case-insensitively against pack-declared aliases is exactly the shape `Lot.layer` / `Lot.areaZone` already are (`schema.prisma:552-553`), and `registry.ts:75-80` `aliasMatches` already implements the matching.

**Why not overload `Lot.areaZone`.** The C1 spec §3.3.2 offers it ("scope the rule explicitly to a Type-A-identified alias"), and it would cost zero migration — `LotSizeCap.areaZoneAliases` already ships and `matchingCap` already honours it. Rejected: `areaZone` is a **location** ("carriageway", "shoulder", "verge") and material type is **orthogonal** to it. A lot that is both "shoulder" and "Type A" could record only one, and the first pack that needs a zone-scoped *and* material-scoped cap would be stuck. One column now beats an ambiguity forever.

**Sourcing.** Human-entered only. Not derived from `layer`, not derived from the ITP — Table 204.142's Type B **sub-rows** are discriminated by position relative to the Type B top / Cut Floor Level, and no mapping from CIVOS data to those sub-rows exists or has been researched (§17.2 R5).

### 3.2 The specified relative compaction band — **no new column**

**Decision: the band is carried by the shipped `Lot.testScale` slot, and `tfnsw-q6.v1` declares its bands as `scaleKeys`.**

The Q6 research shows band selection is required to pick a Table Q6/L.1 row. It does not follow that a new column is required. Look at what `testScale` already is, in the shipped code's own words (`schema.prisma:572-575`): *"the testing scale the governing specification regiments by"*, validated against the resolved ruleset's `scaleKeys`, never silently coerced. That is precisely, and only, **the per-lot specification-declared parameter that selects the count row**. VicRoads regiments by Compaction Scale A/B/C; TfNSW Q6 regiments by specified relative compaction band. Same slot, different authority vocabulary — exactly the shape `scaleKeys` was built for (`Ruleset.scaleKeys`, "what a lot may declare").

Reusing it means the entire band half of D14 is **pack content, not code**. It inherits, at zero cost:

- the column, the migration, the index — already live;
- the **shape** check on all five write paths — `testSufficiencyLotFields` (`validation.ts:86-90`), which create, bulk-create, PATCH, bulk-set **and** the copilot lot-breakdown executor all route through `[D14R-R13]`;
- the entry control — `LotEditFormFields.tsx:244-262` renders `scaleKeys` as a `<select>`, and `BulkActionModals.tsx` the same;
- the honest-degradation semantics — `scale_not_selected` / `scale_not_recognised` → `unknown`, never a guessed count (`evaluate.ts:102-108`);
- the Wave B importer column, when it lands.

**What it does NOT inherit, corrected from Rev 1 `[D14R-B5]`.** Rev 1 claimed the reuse inherits "validation at the trust boundary … whole-batch". It does not. `assertTestScaleValidForLots` is **module-private** in `bulkMutationRoutes.ts:45` with **one** call site (`:213`, the bulk-set route). `createRoutes.ts:141`, `lots.ts:208` (PATCH), `bulkCreateCore.ts:198` and `copilot/lotBreakdownExecutor.ts:22` all write `testScale` with **no** `scaleKeys` check, so `testScale: 'A'` on an NSW lot is API-reachable today — which is what makes `[D14R-B2]` reachable. §9.2 hoists the validator; §10's row states what actually ships.

**Two things the reuse must fix; one is cheap, one was under-costed:**

1. **The control's label — and the readiness prompts.** `"Testing Scale"` is hard-coded at `LotEditFormFields.tsx:241-243` **and** at `BulkActionModals.tsx:326`, and the readiness prompts that name the concept are a static `Record` with no ruleset input (`conformanceItems.ts:219-226`). → `Ruleset.scaleLabel` (§4.2) threaded through all three (§4.7, §9.3). **Rev 1's "six lines total" is withdrawn** `[D14R-B6]`: the failing scenario is an NSW lot whose panel says *"Select this lot's testing scale"* beside a form control labelled *"Specified relative compaction"* offering `>95.0-98.0%` — exit item 12 ("readable by a quality manager without training") fails on the first NSW lot the pack ever touches.
2. **Band-edge legibility.** A user reading "98 %" off a drawing must land on the right row, and Q6's edges are exclusive-below/inclusive-above (`> 95.0, ≤ 98.0`). → the scale **keys themselves are the band labels**, in ASCII, spelling both bounds: `'<=90.0%'`, `'>90.0-95.0%'`, `'>95.0-98.0%'`, `'>98.0-100.0%'`, `'>100.0%'`. They render verbatim in the `<select>` and in `assertTestScaleValidForLots`'s error message ("Valid scales: …"), and they are valid object keys for `minCountByScale`/`countByAreaBand`.

**Rejected alternative, recorded with its flip condition.** A numeric `Lot.specifiedCompactionPct Decimal?` with the band derived by the engine is *more* precise: the user records `98.0` and CIVOS does the band arithmetic and can say "98.0 % specified → Table Q6/L.1 row `> 95.0, ≤ 98.0`". It costs a migration, a validation rule, a form field, an importer column, a band-derivation function, a new `UnknownCause`, and a second per-lot concept sitting beside `testScale` that means almost the same thing. **Flip to it when any of these becomes true:**

- a pilot mis-picks bands (measurable: lots whose band contradicts their ITP acceptance criterion);
- the band is ever to be **derived** rather than entered — e.g. from R44 Table R44.7's location→% mapping, which would need the research pass of §17.2 R1;
- a second NSW authority pack needs both a scale **and** a band on the same lot.

**Consequence, stated plainly:** `tfnsw-q6.v1` declares **no `defaultScale`**. Q6 publishes no "where unspecified, assume X" sentence (unlike Section 204's Scale A default, which is quoted verbatim in `vicroads-204.v1.ts:128-131`). So an NSW lot with no band reads `unknown` / `scale_not_selected` and shows the existing prompt — *"Select this lot's testing scale to check its test frequency"* (`conformanceItems.ts:223`) — until a human enters it. That is the honest case §16 D6 explicitly preserved.

### 3.3 `Lot.smallAreaElected` — the Section 173 election (specified; **DEFERRED by Jay**, §16.0 J3)

> **J3 is resolved as of Rev 2: small-lot handling is ADVISORY ONLY. Phase D14.4 does not start** until a pilot asks for the count reduction. The section below is kept in full — unchanged and unbuilt — so that whoever picks it up later inherits a specified phase rather than a fresh design problem. Everything §11 marks D14.4 is on the same footing.


```prisma
// D14 phase 4 (ONLY if Jay greenlights — see the spec's §16.0 J3): the
// contractor's election to test this lot as a Section 173 SMALL AREA.
// cl. 173.04(d) is PERMISSIVE — "any lot which has a surface area less than
// 500 m2 MAY be treated as a small area" — and the election buys a HARDER
// acceptance target (mean of 3 beating the scale requirement by 2.0 points),
// so it is a real commercial choice, not a formality. It cannot be inferred
// from any field CIVOS holds.
// NULL or false => the full count applies (§3.4). Never the reverse.
smallAreaElected Boolean @default(false) @map("small_area_elected")
```

**Why this cannot be derived from area.** `docs/research/c1-sec173-small-lots-2026-07-27.md` §3.1 is binding: *"an area-triggered auto-reduction would be wrong and dangerous. If CIVOS sees `area = 300 m²` and silently emits `requiredCount = 3`, it under-states the requirement for every small lot the project chose to test normally."* That is the same ruling `[C1C-6]` made for the reduced-frequency regime — **compute eligibility, never auto-grant** — and this limb follows the identical pattern.

**Why it is deferred rather than built.** The research's own recommendation (§3.4 G1): *"ship the advisory first, add the flag when someone asks for it. The advisory needs no schema change at all."* §6.2 ships the advisory in phase D14.2; §11's phase D14.4 builds the flag and its application. **Jay resolved J3 the same way on 2026-07-27: advisory only, and D14.4 waits for a pilot to ask.**

**No route-level area guard.** An election recorded on a 700 m² lot is **inert**, not an error: eligibility is re-derived at read time from the current area, so a stored guard would go stale the moment someone edits the quantity — the same argument §3.4.1 makes for computing rather than storing the regime. The flag is accepted freely and applied only where eligibility holds.

### 3.4 NULL semantics — err to full frequency, uniformly

Consistent with `activitySlug` (C1 spec §16 D7: an unresolvable classification never earns a relaxation).

| Attribute | NULL / absent means | Effect on `requiredCount` | Effect on gating |
| --- | --- | --- | --- |
| `materialType` | not recorded | **none** — a material-scoped cap simply does not match | none: `lot_exceeds_max_lot_size` never blocks (`conformanceItems.ts:338-350`) |
| `testScale` (VIC) | `ruleset.defaultScale` = `'A'` applies, `source: 'ruleset_default'` | full Scale A count | unchanged |
| `testScale` (NSW/Q6) | no default declared → `scale_not_selected` | `null` — `unknown` | never blocks, never satisfied (`evaluate.ts:147-152`) |
| quantity, for a Q6 rule | no area resolvable **in m²** from either the lot's own quantity or its geometry (§4.6) | `null` — `unknown`, cause `quantity_missing` | never blocks, never satisfied |
| quantity, for the Section 173 limb | **not eligible** — advisory silently absent | full count | unchanged |
| `smallAreaElected` NULL/`false` | not elected | **full** count (6, not 3) | unchanged |

**Rev 2 correction to this row `[D14R-B4]`.** Rev 1 read "quantity, for a Q6 rule → `quantity_missing`" as if the lot's own recorded quantity were the only source. The shipped resolver (`resolve.ts:170-175`) makes the lot's own quantity win **outright**: `LotGeometry.areaM2` is consulted only when the lot quantity is absent or ≤ 0. So a lot carrying `quantityValue: 4500, quantityUnit: 'm3'` **and** a drawn polygon resolves to `{4500, 'm3'}`, mismatches the Q6 rule's `m2`, and reads `unknown` — while being told to *"Record this lot's quantity (or draw its geometry)"*, which it has already done twice. `docs/research/c1-sec173-small-lots-2026-07-27.md` §3.4 **G2** names this as common, not a corner case: *"Earthworks lots are commonly recorded as volume or chainage length."* **§4.6 fixes the resolution; §4.7 fixes the prompt.** Without both, Q6 is inert on a large share of real NSW lots while every test passes.

**One rule the evaluator must honour and a build agent will be tempted to break:** a missing area suppresses the **Section 173 advisory silently** and must **not** push a `quantity_missing` cause. VicRoads' compaction rule carries no `perQuantity` limb, so quantity is not required for its count; making the small-area *advisory* demand it would flip a perfectly evaluable Scale A lot to `unknown` and delete a working number from the panel. Advisory absence is the correct degradation (research §3.4 G2: *"area unknown → not eligible → standard count, never a guess"*).

**Why not "err to the strictest band" for a missing Q6 band.** Superficially that is the safest direction — assume `> 100.0 %`, require 10. Rejected: it asserts a requirement this lot's specification did not state, on a surface that can eventually gate a claim. §7.1's doctrine is `unknown`, never a guessed number, and it applies here without exception.

#### 4.3.1 Registry validation additions (`registry.ts` `validateRule`)

- **exactly one** of `minCountByScale` / `countByAreaBand` per rule — never both, never neither;
- **`countByAreaBand` may not co-exist with `perQuantity`** `[D14R-R2]`. The shipped outer `perQuantity` block (`evaluate.ts:119-129`) runs independently of the banded branch and would push `quantity_missing` beside it; a banded rule carries its rate **inside** the band, never outside;
- **`countByAreaBand` may not co-exist with `smallLot`** `[D14R-R2]`. §4.4's substitution replaces `minCountByScale[scaleValue]`, which a banded rule does not have. No pack needs both; when one does, the interaction must be designed rather than fallen into;
- **`countByAreaBand` is forbidden on a `reduced` limb.** Rev 1 permitted it "(no shipped pack does)". Rev 2 forbids it, which is one type change cheaper — see the note below;
- `countByAreaBand.unit` is a `QuantityUnit`;
- **exactly one** of `byScale` / `bands` per `countByAreaBand`;
- `byScale`, when present, declares a **non-empty** band list for every `ruleset.scaleKeys` entry and no key outside it (mirrors the shipped `checkCounts` at `:129-143`); `bands`, when present, is non-empty;
- within a band list: `upToInclusive` **strictly ascending**; **exactly one** band omits it; that band is **last**;
- every `minCount` an integer ≥ 1; every present `every` > 0.

> **Why `ReducedFrequency.minCountByScale` stays required** `[D14R-B3]`. `figures` (`evaluate.ts:118`) is the union `FrequencyRule | ReducedFrequency`. Making the `FrequencyRule` member optional already gives `figures.minCountByScale` the type `Readonly<Record<string, number>> | undefined`, which forces the §4.3.1a guard — so `types.ts:60` needs **no** change, and the `reduced`-limb validation branch Rev 1 proposed does not need writing. `ponytail:` forbid the combination nobody needs; add the limb when a pack actually publishes a banded reduced table.

#### 4.3.1a The two shipped readers that MUST become conditional `[D14R-B3]`

Rev 1 said "the arithmetic … and the `max()` semantics are the shipped ones; only the **selection** is new" and did not name these. Both are unconditional today, and a build agent following Rev 1 literally ships a pack that **cannot register**. Exactly two edits, both one line:

1. **`backend/src/lib/readiness/sufficiency/evaluate.ts:141`** — today:
   ```ts
   const minCount = scaleValue === null ? null : (figures.minCountByScale[scaleValue] ?? null);
   ```
   Once the `FrequencyRule` member is optional this is a type error and, at runtime, indexes `undefined`. It becomes conditional on the limb being present, and the banded branch (§4.3.2) supplies its own `minCount`.
2. **`backend/src/lib/readiness/sufficiency/registry.ts:144`** — today:
   ```ts
   checkCounts(rule.minCountByScale, 'minCountByScale');
   ```
   `checkCounts` (`:129-143`) requires a count for **every** `scaleKeys` entry, so `tfnsw-q6.v1` — which supplies its counts through `countByAreaBand` — would fail `validateRuleset` with five *"declares no count for scale …"* problems and never register. The call becomes conditional on `rule.minCountByScale` being present; the exactly-one-of check above is what keeps a rule from declaring neither.

AT-41 asserts both directions: a banded pack registers, and a rule declaring neither limb is rejected.

#### 4.3.2 Evaluator change (`evaluate.ts` `evaluateRule`)

Slots in at the existing `figures` seam (`:118`), between the quantity block and the counts block. Two guards Rev 1 was missing are marked:

```

~20 lines. The arithmetic, the `every > 0` guard and the `max()` semantics are the shipped ones; the **selection** of `(minCount, every)`, the two guards and the per-unit `q` are new.

**Why the guard matters more than it looks** `[D14R-B2]`. `evaluateSufficiency` runs inside `computeConformanceResult`, which is deliberately DB-free and shared by the single-conform path **and** the batched claim path. One lot with `testScale: 'A'` on an NSW project would 500 the lot readiness route — and 500 **claim create** at the 5,000-member ceiling (§12). The guard is the fix; §9.2's hoisted validator is the prevention; neither alone is enough, because the validator cannot retroactively clean rows written before it shipped.

### 4.4 `FrequencyRule.smallLot` — the Section 173 limb

Encoded exactly as `docs/research/c1-sec173-small-lots-2026-07-27.md` §3.2 proposes, with one addition: its **own provenance**, because Section 173 is a *different document* from the rule's Section 204 (the shipped `ReducedFrequencyEligibility` (`types.ts:82-87`) carries only a `clause` string because 204.14(c) is the same document; this limb cannot).

   * requirements are based on CHARACTERISTIC values", while Table 204.131's
   * Scale C column is headed "Minimum MEAN Value of Density Ratio". Scale C is

   * `C: 3` "for completeness" — it would imply a reduction that does not exist.

  minCountByScale: Readonly<Record<string, number>>;

   * points, and the statistic changes from characteristic (x̄ − 0.92S) to plain

  /** Section 173's own provenance — a DIFFERENT document from the rule's. */

`validateRule` additions: `maxArea.unit` a `QuantityUnit` and `maxArea.value > 0`; `minCountByScale` non-empty, every value an integer ≥ 1, every key inside `ruleset.scaleKeys`, and **not required to cover every key** (that is the whole point — Scale C is absent); `acceptanceShiftPct` finite and ≥ 0; `provenance` run through the shipped `validateProvenance`, so a `confirmed` pack's Section 173 citation must itself be grade A, pdf-paged, and unexpired.

                    && areaForSmallLot < smallLot.maxArea.value

(smallLot.minCountByScale[scaleValue] ?? minCountByScale[scaleValue]) : …` and justified it as covering "a Scale C lot that somehow carries the election". ### 4.6 Per-unit quantity resolution — the fix that makes Q6 work at all `[D14R-B4]`

**The defect.** `resolveSufficiencySync` (`resolve.ts:161-175`) resolves **one** quantity for the whole lot, and the lot's own value wins outright:

```ts
const quantity =
  lotQuantity !== null && lotQuantity > 0 && lotUnit
    ? { value: lotQuantity, unit: lotUnit, source: 'lot' as const }
    : geometryArea !== null && geometryArea > 0
      ? { value: geometryArea, unit: 'm2' as QuantityUnit, source: 'geometry' as const }
      : { value: null, unit: null, source: 'none' as const };
```

An NSW earthworks lot recorded as `4500 m3` — the ordinary way a bulk-earthworks lot is measured — with a drawn polygon carrying its `areaM2` resolves to `{4500, 'm3'}`. Every Q6 rule needs `m2`. The lot reads `unknown` forever, and §1's headline outcome ("an NSW earthworks lot gets a real, spec-cited required test count") does not happen. Chainage-length lots fail identically. This is the one defect that would ship a **green test suite and a dead feature**.

**The fix, smallest form.** Keep the single `resolved.quantity` exactly as it is — every shipped consumer keeps working — and add **one** field plus **one** helper.

```ts
// sufficiency/types.ts — on ResolvedSufficiency, beside the shipped `quantity`:
/**
 * D14: the summed `LotGeometry.areaM2`, kept SEPARATELY from `quantity` because
 * the lot's own quantity legitimately wins for `quantity` (§6, D5) while still
 * being the WRONG UNIT for a given rule. A rule needing m² can fall back here
 * even when the lot itself is measured in m³ or chainage metres. NULL when the
 * lot has no geometry, or none carrying an area.
 */
geometryAreaM2: number | null;
```

`resolve.ts` already computes `geometryArea` at `:165-169` for the existing fallback; the field is that value, returned rather than discarded. **No new query** — `geometries` is already in the select (§8).

```ts
// sufficiency/evaluate.ts — module-local, used by §4.3.2, §4.4 and the perQuantity block:
function quantityFor(resolved: ResolvedSufficiency, unit: QuantityUnit): number | null {
  if (resolved.quantity.value !== null && resolved.quantity.unit === unit) {
    return resolved.quantity.value;
  }
  // ponytail: the ONLY cross-source fallback, and it is not a conversion — the
  // geometry is genuinely measured in m². Never convert m3 -> m2 or m -> m2:
  // that needs a depth or a width CIVOS does not hold (§5.3, cl. 5.4.2).
  if (unit === 'm2' && resolved.geometryAreaM2 !== null && resolved.geometryAreaM2 > 0) {
    return resolved.geometryAreaM2;
  }
  return null;
}
```

**Three call sites, all inside `evaluateRule`:** the shipped `perQuantity` block (`evaluate.ts:119-129`, whose `quantityUsable` test becomes `quantityFor(perQuantity.unit) !== null`), the banded branch (§4.3.2), and the small-lot limb (§4.4). `requiredTestCount` (`counts.ts:50-60`) is called with the per-unit value and is otherwise **unchanged**.

**What this deliberately does not do.** It does not convert between units, it does not let a lot record two quantities, and it does not make a tonnage-keyed rule work on an areal lot (§5.6.3 — that is the real reason four pavement rules stay out of scope, **not** a missing `QuantityUnit`; see §0.3 item 1). `RuleSufficiency` carries no new field: the quantity a rule actually counted against is already implied by the rule's own unit.

**Behaviour change for the shipped VicRoads pack: none.** `vicroads-204.v1`'s compaction rule carries no `perQuantity` limb, so `quantityFor` is never called on the VIC path. AT-45's byte-identical assertion covers it.

### 4.7 Threading the pack's vocabulary into the readiness prompts `[D14R-B6]`

`UNKNOWN_CAUSE_PROMPT` (`conformanceItems.ts:219-226`) is a static `Record<UnknownCause, string>` with no ruleset input. Two of its six strings name concepts the pack owns, and one asks for something the user may already have done:

| Cause | Shipped string | Wrong how |
| --- | --- | --- |
| `scale_not_selected` | *"Select this lot's testing scale to check its test frequency."* | On NSW the concept is *specified relative compaction*, and the form control beside it says so. |
| `scale_not_recognised` | *"This lot's testing scale is not one the governing specification uses."* | Same, plus it should name the valid list the way `assertTestScaleValidForLots` does. |
| `quantity_missing` | *"Record this lot's quantity (or draw its geometry) to check test frequency."* | After §4.6, an m² rule genuinely has no area when this fires, so the string is correct **for m²** — and actively wrong for a rule needing tonnes or chainage metres, where drawing a polygon changes nothing. |

**The change.** `UNKNOWN_CAUSE_PROMPT` becomes a function:

```ts
function unknownCausePrompt(
  cause: UnknownCause,
  ctx: { scaleLabel: string; requiredUnit: QuantityUnit | null },
): string
```

`scaleLabel` is `ruleset.scaleLabel ?? 'testing scale'`; `requiredUnit` is the unit the unsatisfied rule needed, or `null`. The item builder **already receives the resolved sufficiency**, which carries the ruleset and the rules, so nothing new is fetched or plumbed through a signature that does not already have it. The empty-string entries (`no_ruleset_for_project`, `no_rule_for_activity`) stay empty — silence is deliberate (§7.1).

`ponytail:` a function of two arguments, not a per-ruleset prompt registry. AT-55 pins the NSW wording end-to-end.

#### 5.2.1 Why `perQuantity` + `minCountByScale` cannot express this `[C1C-13]`

The C1 spec §8.2 (line 942) and the TfNSW report **§4 item 3** both state the Q6 shape "which `perQuantity` + `minCountByScale` already express", and offer `> 95.0–100.0 %` → `perQuantity: 1 per 2,000 m²` with `minCount: 6`. **That is correct for the `> 5,000 m²` column only.**

*(Citation note `[D14R-R5]`: the TfNSW confirmation report's §4 is a flat five-item list with no §4.3. Rev 1 cited it both ways; Rev 2 says **"§4 item 3"** throughout. Counter-example: a **400 m²** lot in band `> 95.0, ≤ 98.0`.

- Published (Table Q6/L.1, column `> 50, ≤ 500 m²`): **3**.
- The proposed encoding: `max(6, ceil(400 / 2000)) = max(6, 1) = ` **6**.

### 5.6 The pavement extension — phase D14.5 (the J4 pass, resolved)

Rev 1 shipped Q6 earthworks-only and listed the pavement question as `[C1C-*]`-adjacent unknown **R2**. **Jay approved the pass (J4); it is complete and grade A** (`docs/research/c1-q6-pavements-2026-07-27.md`). R2 is struck from §17.2 and moves to §17.1 settled.

#### 5.6.1 What the research settles

**Q6 owns pavement sampling frequency, through the very Table Q6/L.1 already encoded.** There is no separate pavement table and nothing new to transcribe. Q6 cl. 3.8.3 (PDF p. 20) is a two-way ownership map that TfNSW wrote deliberately into Ed 2 — its own revision register calls the clause an Ed 2 clarification:

| Work output | Frequency owner |
| --- | --- |
| Constructed pavement layers (areal) — compaction, moisture, density | **Q6 Annexure Q6/L, Table Q6/L.1** — already encoded (§5.2) |
| Granular material supply / stockpiles (not areal, lotted by mass) | TfNSW 3051 Annexure 3051/L — **out of scope** (§5.6.3) |
| Everything else on a pavement (thickness, level, ride, width, binder) | the respective R-spec's Annexure /L — **partly in scope** (§5.6.3) |

R71, R73 and R75 each delegate with the literal phrase *"As per TfNSW Q for specified relative compaction"* — the same delegation pattern R44 uses for earthworks, now confirmed on three more documents.

**And the row collapses to one.** Every specified relative compaction those specs publish is ≥ 100 % — R71 Table R71.1 gives 100 % (Modified) or 102 % (Standard); R73 cl. 8.4.3 and R75 cl. 7.4.3 give ≥ 102 % for courses ≤ 250 mm. So a TfNSW pavement lot lands on Table Q6/L.1's **`> 100.0` row** in every case but one (R75 courses > 250 mm, which falls to `> 98.0, ≤ 100.0`). **R71's Annexure R71/L heavy-duty override republishes that row's five cells verbatim** — two independent primary documents publishing the same five numbers is the strongest cross-check available, and it is the reason this extension is nearly free.

Two Q6 exceptions are proven **structurally unreachable** for pavements and must not be encoded: cl. 5.4.3(a) (non-contiguous lots) requires compaction *< 100.0 %*, and cl. 5.4.3(b) + Table Q6/L.1 note (1) (multi-layer minimums) require *below 98.0 %*. Neither can engage at 100 % / 102 %. **Consequence: the multi-layer under-statement §5.3 carries for earthworks does not exist on the pavement rules**, and the pavement rule label says so.

**Not a second ruleset** `[refuted, §0.3 item 2]`. #### 5.6.4 The Q6 50 % reduction — specified as deliberately absent

Q6 cl. 3.8.3 publishes a real, numeric reduction mechanism, and §5.3's corrected row records it. It is **not encoded, and not as an eligibility advisory either.**

The shape looks like `[C1C-6]`'s *eligible-to-request-never-automatic* pattern, and the research reads it that way. It is **weaker than that pattern**, in the one respect that matters: `ReducedFrequencyEligibility` exists because VicRoads 204.14(c)'s trigger — *N consecutive conforming lots* — is a thing CIVOS **can compute** from data it holds, which is what makes an advisory honest ("you may now be eligible to ask"). Q6 cl. 3.8.3's trigger is *"a statistical analysis verifying consistent process capability"*, judged by the Principal, revocable at any time. CIVOS can compute **no part** of it. An advisory saying "you may be able to propose a reduction" is true of every TfNSW project on every day and carries no information; encoding it as `reduced` **figures** would be far worse — a 50 % count reduction no lot record can justify, in the under-testing direction.

**Decision (D14q): recorded in the `tfnsw-q6.v1` header with its clause and its 50 % figure, encoded nowhere.** The header text exists so the next agent finds "FOUND, deliberately not encoded, here is why" rather than "NOT FOUND" and re-derives it — which is exactly the failure the earthworks report's item 7 set up. **Flip condition:** if TfNSW ever publishes a self-executing trigger, or a pilot records the Principal's approval as structured data, this becomes an ordinary `reduced` limb plus an eligibility source, and `[C1C-6]`'s pattern applies unchanged.

**3051's quantified reduced column is a trap and must not be borrowed.** Table 3051/L.1 publishes real reduced figures gated on *"six consecutive Lots conforming"* — genuinely computable-looking. It governs **mass-lotted material supply**, not constructed pavement lots, and §5.6.3 rules that table out of the counter entirely. Transplanting its reductions onto an areal rule would be the same class of error as the R44 misattribution.

### 6.1 The Type-A 5,000 m² cap — `[C1C-3]` closed

```ts
// On COMPACTION_DENSITY (`vicroads-204.v1.ts:101-121`):
maxLotSize: [
  {
    unit: 'm2',
    value: 5000,
    // Table 204.142, row "Type A Material": "One day's production or 5,000 m²,
    // whichever is the lesser". The day's-production limb is unevaluable (§3.3)
    // and the area limb is TYPE A ONLY — Type B's two capped sub-rows are
    // 10,000 m² and Type C has no area cap at all [C1C-3].
    materialAliases: ['type a', 'type a material'],
  },
],
```

**Type B is not encoded, and the reason is not laziness.** Table 204.142 splits Type B into three rows: *ripped and re-compacted below Cut Floor Level* → 10,000 m²; *placed within 400 mm of top of Type B Material* → 10,000 m²; *placed more than 400 mm below top of Type B material* → **one day's production, no area cap**. A cap keyed to `materialAliases: ['type b']` would therefore be **wrong for the third sub-row** — firing a fabricated 10,000 m² cap on material the specification caps only by production day. The sub-rows are discriminated by vertical position relative to the Type B top / Cut Floor Level, which maps to nothing CIVOS records (§17.2 R5). **Type C is not encoded** because there is nothing to encode — it has no area cap.

`Ruleset.materialTypes: ['Type A', 'Type B', 'Type C']` ships anyway: the control must offer all three so a user can record Type B and thereby **suppress** the Type A cap, which is the whole point of the discriminator.

**The residual under-warning, stated `[D14R-R9]`.** Two of Table 204.142's three Type B sub-rows *do* carry a **10,000 m²** cap, and shipping `'Type B'` as a selectable value so it can suppress the Type-A cap also suppresses that one — which was never encoded. **Concretely: a 12,000 m² Type B lot warns about nothing, and it should warn.** §6.1's refusal to encode a `['type b'] → 10,000` cap is still right (it would fabricate a cap on the third sub-row, which the specification caps only by production day), but the consequence belongs in writing rather than only in the reasoning. The direction is safe — a missing advisory warning, never a missing count and never a block — and it closes when §17.2 **R5** is researched.

Warning copy is the shipped generic one (`conformanceItems.ts:338-350`), which already names the limit, the actual and the unit. Severity `warning`, `blocksAction: false` — advisory, always (C1 spec §3.3).

### 6.3 The +2.0 % shift is not computed — the misleading-verdict mitigation (research G3/G4)

This is the one place in the slice where a correct verdict can be **read** wrongly, and it is stated rather than hidden.

CIVOS's engine counts tests. It does not evaluate density-ratio values against Table 204.131, does not compute a characteristic value `x̄ − 0.92S`, and does not compute a mean. So a small-area lot can legitimately show **"3 of 3 — test frequency met"** while its mean is 99.5 % against a required 101.0 %. The verdict is *true* — it is a statement about count sufficiency — and a user will read it as "passing".

**Binding on the implementation:**

- Whenever the small-area limb is **eligible or applied**, the item text **must** state the shifted acceptance threshold in the same sentence as the reduced count. Never a bare "3 tests required".
- The satisfied-case sentence for an applied small-area rule **must** carry the qualifier: *"CIVOS counts tests; it does not check that the mean beats the scale requirement by 2.0 %."*
- **G4 recorded separately:** even once CIVOS evaluates values, the small-area case must switch **statistic** (characteristic → mean), not merely shift the threshold. A future implementer who only shifts the threshold will be wrong.
- Computing either properly needs material type × scale × density-ratio values — a C2/C3 capability, not a C1 one.

`ponytail:` state the threshold in the sentence; do not build a value-evaluation engine to avoid one misreading.

### 6.4 The 204.14(c) streak exclusion (phase D14.4, with the flag)

`[C1C-6]` records that Section 173 small areas *"shall not be included"* in the 204.14(c) consecutive-conforming-lots streak, and that CIVOS's computed streak is therefore an **upper bound**. Once `smallAreaElected` exists that ceases to be an approximation (research §3.5): the exclusion is mechanical.

- **The query filter is the whole mechanism.** The Prisma stream query filters `smallAreaElected: { not: true }` in the `where`, so `take: N` returns the last N **non-elected** entries — complete *and* bounded, and the §3.4.1 proof restates verbatim with "non-elected" inserted. The filter is a heap predicate on top of `lots_project_activity_slug_conformed_idx`; at the 5,000-lot reference dataset that is immaterial, and §12 asserts the query shape plus the p95.
- **`RegimeStreamEntry` gains NOTHING, and there is no in-evaluator skip** `[D14R-R8]`. Rev 1 specified both the field and the filter. The field is not merely redundant — filtered rows never arrive, so it would be permanently `false` — it is **worse than the filter**: an in-evaluator skip over an unfiltered `take: N` window would leave the window **short** by however many elected lots it swallowed, quietly weakening the streak. Note this is the opposite call from `RegimeStreamEntry.activitySlug` (`regime.ts:56-62`), which is deliberately *not* filtered because a NULL slug means the window is **incomplete** and `reduced` must not be earned across it. The difference is real: an unclassified lot is unknown history; an elected small area is known non-history.
- **Nothing here weakens `[C1C-6]`.** 204.14(c) still requires the Superintendent's agreement and an established compaction procedure, and still counts only lots conforming **in the first test** — neither observable. The regime output stays **advisory**, and `reduced` still requires `ReducedFrequency` **figures**, which no shipped pack declares.

### 6.5 Edit `vicroads-204.v1` in place — with an expiry date

C1 spec §8.3 step 3 forbids in-place edits of a shipped `.vN`, because *"snapshots reference `ruleId` strings that must keep resolving"* and F0's rule is **"definitions are never edited in place once instances exist."**

**No instances exist.** C1.2 has not shipped (§2.2): no requirement-set module emits a `sufficiency` key, so no `RequirementEvaluation` row references `vicroads-204.v1/compaction-density`. Minting a `.v2` today would add a file, an `effectiveTo`, and a second live pack, to protect zero rows.

If it has, **mint `vicroads-204.v2.ts`** with `effectiveTo` on v1 instead — `resolveRuleset` (`registry.ts:46-66`) already picks the newest effective pack and the older one keeps resolving for historical `ruleId`s.
2. **The exemption expires with C1.2.** Once the `sufficiency` snapshot key ships, every subsequent pack change emits `.vN+1`, no exceptions. Recorded in the pack file header so the next agent does not read this PR as a precedent.

# 3D/4D IFC capability — build-ready spec, Rev 2 (2026-08-06)

Status: **spec only — build not triggered.** Trigger (per
[`../research/tmr-digital-engineering-recon-2026-08-06.md`](../research/tmr-digital-engineering-recon-2026-08-06.md)):
the first tender/prospect naming TMR BIM deliverables, DMS-ST-207, or handover models.

**Rev 2.** Rev 1 was adversarially reviewed per the repo's SOL gate (gpt-5.6-sol, verdict on Rev 1:
RETHINK, 14 findings) and corrected against a parallel primary-source research pass on the TMR
EIR + BIM Guideline. The disposition of every finding is in Appendix C. The two biggest reframes:

1. **A lot-derived IFC is not an "As Constructed survey."** EIR §9.1.2 requires survey results
   *"conducted by a qualified surveyor"* on GDA2020/MGA + AHD at LOD 500 (field-verified). Geometry
   derived from our chainage/offset lot records is a *draft/preview* artefact. The compliance-grade
   export requires **survey-authoritative geometry ingestion** (12d/LandXML/CSV pickups with E/N/RL,
   datum, epoch, accuracy, surveyor identity) — now a first-class part of Phase 1, wired into the
   lot survey records feature we already ship.
2. **CIVOS supplies a component, not the submission.** The §9.1.2 As Constructed submission also
   contains 12d ASCII models, a federated survey-derived model, AS5488 utility models — surveyor and
   lead-appointed-party deliverables. Our export + validation report + file register feed the lead
   appointed party's submission through their CDE (TMR mandates InEight); we do not build a
   transmittal portal and we do not claim the zip is "the submission".

Primary sources: `docs/research/tmr-source-docs/` (EIR May 2026 + BIM Guideline, full text);
TMR Revit-to-IFC Export Pack V6.0 layer mapping; library repos/registries (checked 2026-08-06);

## 1. Capability definition

| # | Product | What it is | Grade |
|---|---|---|---|
| P1 | **Per-lot IFC 2x3 as-constructed export** | One IFC 2x3 file (or BEP-configured aggregation) per completed construction lot: geometry + **TMR's four named property sets** (`Project` / `Design` / `Construction` / `Asset Management`, Guideline §6.4.1) + a supplementary CIVOS QA set + machine-generated validation report, file register and manifest | Two explicit grades: **DRAFT** (lot-derived geometry, watermarked, for demos/coordination) and **SUBMISSION** (survey-ingested geometry, surveyor certification captured, immutable snapshot) |
| P2 | **Browser IFC viewer** | Client-supplied design models (IFC 2x3 + IFC4/4x) in a lazy route, desktop + mobile, models in the Supabase `documents` bucket behind backend-mediated access, with a dedicated resumable-upload path for large files | Product feature |
| P3 | **4D QA timeline** | IFC GlobalId ↔ lot links; per-element colour driven by lot status at time T, scrubbed over the status history; built on the **existing** `statusTimeline` endpoint + a new transactional `LotStatusEvent` ledger | Product feature |

**Positioning.** TMR governs civil objects **by property set and unique object code, not by IFC
class** (neither TMR document names a single `Ifc*` entity). `ConstructionLotNumber`'s documented
example value in the Guideline is literally *"To Contractors QA system"* — TMR's own tables point at
the system CIVOS is. CivilPro's 3D/4D (GA target H2 2026) generates geometry procedurally for
tier-1s; our wedge is that the QA attribute payload — the part TMR actually specifies — is our
native data, and our viewer/4D works on a phone.

## 2. Compliance target (verbatim, with honest scope)

**EIR §9.1.2 (Construction — As Constructed model submission), the full deliverable list:** the As
Constructed records — *"the results of As Constructed surveys conducted by a qualified surveyor"* —
must include: 12d ASCII digital models on the project datum · a federated As Constructed 3D
attributed model · asset attributes per the BIM Guideline and TMR object attribute publications ·
*"**As Constructed survey of completed construction lots in an Industry Foundation Class \*.ifc 2x3
open file format**"* · AS5488 QL-A utility models.

Scope consequences:
- The IFC 2x3 per-lot clause is the only bullet scoped to construction lots — that is our product.
- The surrounding bullets are surveyor/designer/lead-party obligations. CIVOS's export is an input
  to their submission. Marketing and UI copy must say "TMR-format as-constructed lot export", never
  "TMR submission".
- **Survey authority:** SUBMISSION-grade export requires surveyed geometry (E/N/RL on GDA2020/MGA +
  AHD per EIR §8.2) ingested from surveyor files, with `ModelCertifiedAsConstructedSurveyor`
  (Guideline §6.4.1: e.g. `Jane Citizen – Reg Surv 3322`) captured — our existing lot survey-records
  feature (surveyor, verdict, report file) is the natural anchor. Lot-derived geometry exports are
  watermarked DRAFT in FILE_DESCRIPTION + manifest and blocked from SUBMISSION packaging.

**EIR §8.6 + §9.3 + Guideline §6.4.1 (property sets):** objects carry named psets rendered as
*"separate tabs … within an IFC model file viewer"*. The Guideline's attribute tables name exactly
four: **`Project`**, **`Design`**, **`Construction`**, **`Asset Management`**, with attribute
spellings incl. `ConstructionLotNumber`, `ConstructionDate`, `UniqueObjectCode`, `ControlLine`,
`StartCHG`/`EndCHG`, `Datum`, `Zone`, `Tdist`, `ModelCertifiedAsConstructedSurveyor`. The §8.6
BEP route (contractor-prepared attribute schedules) covers **objects TMR has not catalogued** and
supplementary sets — it is conditional on BEP acceptance, not automatic. The normative
per-discipline *civil object attribute files* are not yet retrieved (D6 — top follow-up; the
Guideline tables are explicitly "not … comprehensive").

**EIR §9.2 (validation):** submissions carry *"model validation documentation that demonstrates the
validation of the contents of the model against a pre-determined schedule of model objects and
attributes"*, a model file register, and transfer-integrity records. **IDS v1.0 (final standard
2024-06; `ifcVersion` supports IFC2X3) is literally this document in machine-checkable form** — we
ship a CIVOS IDS with every package and validate against it (see §4.4).

**EIR §8.3 (file naming):** ten fields, values project-specific and partly published outside these
documents; separator not in our extracts. Naming is **configurable per project**, never hardcoded.

## 4. Phase 1 — per-lot IFC 2x3 export

### 4.1 Entity model (all verified against IFC2X3 TC1 schema + spike + CV-2.0 agreements)

Spatial tree: `IfcProject` → `IfcSite` → **`IfcBuilding` → `IfcBuildingStorey`** →
products. IfcBuilding is required by **Coordination View agreement #CV-2x3-142** when the header
declares `ViewDefinition [CoordinationView_V2.0]` (the only IFC2X3 value on the buildingSMART header
allowlist) — schema validators cannot see this rule, which is exactly why the Rev 1 spike passed
IfcOpenShell clean while being non-conformant. Storey included for authoring-tool import safety.

Per lot: `IfcBuildingElementProxy` (Name = lot number) — **TMR's own published convention**: their
Revit-to-IFC Export Pack maps Roads/Topography/Parking/Generic → `IfcBuildingElementProxy` (64
occurrences; second most frequent class in their own mapping file). Geometry: SweptSolid
`IfcExtrudedAreaSolid` over `IfcArbitraryClosedProfileDef` (polyline closed **by reference** —
Gherkin GEM111), through `IfcGeometricRepresentationSubContext('Body','Model',…,.MODEL_VIEW.)`.

One-proxy-per-lot is the **default granularity, not an assumption that a lot is an asset object**.
Where a project's BEP/MPDT object-and-attribute schedule defines finer granularity (a lot containing
multiple surveyed features/assets), the export maps **each surveyed feature to its own IFC product**
per that schedule, and the lot is represented as the QA *association* across those products (shared
`ConstructionLotNumber` value + `CIVOS_QA` lot linkage), never as one merged solid. The
feature-to-product mapping is BEP-driven project configuration resolved at onboarding (D6), and a
SUBMISSION export without a resolved mapping fails per §4.4.

Property sets per product — **five**:

| Pset (exact name) | Contents (TMR spellings) |
|---|---|
| `Project` | `District`, `AssetOwner`, `RoadSectionID`, **`Datum`** (`GDA2020`), **`Zone`** (e.g. `56`), `ModelCertifiedAsConstructedSurveyor` (from the lot's survey record) — in 2x3 the pset **is** the georeference mechanism (no IfcMapConversion) |
| `Design` | `UniqueObjectCode` (EIR §8.4 structure, configurable), `ControlLine`, `StartCHG`, `EndCHG`, `Tdist`, layer block where applicable |
| `Construction` | **`ConstructionLotNumber`**, **`ConstructionDate`** |
| `Asset Management` | `UniqueObjectCode`, `TdistStart`/`TdistEnd`, `Offset` |
| `CIVOS_QA` (supplementary; scheduled via BEP per §8.6) | `ConformanceStatus`, `ConformedAt/By`, `ConformanceOverridden`(+reason — never hidden in an evidence artefact), `ITPCompletion`, `TestReferences`, `NCRReferences`, `HoldPointReferences`, `CivosLotId`, `CivosUrl` |

GUIDs: deterministic, **domain-separated** UUIDv5 under the CIVOS IFC namespace UUID
**`cbac43a1-b292-5a17-90bc-d5771c28906d`** (= `uuidv5(NAMESPACE_DNS, "ifc.civos.com.au")`; published
here, fixed forever — never regenerate), encoded with the IFC base-64 alphabet (digits-first, `_$`;
first char 0–3). Canonical identity-key grammar — keys always use immutable DB ids, never display
names; one key per `IfcRoot` category:

| `IfcRoot` category | Identity key |
|---|---|
| Spatial roots | `project:<projectId>` · `site:<projectId>` · `building:<projectId>` · `storey:<projectId>` |
| Product (lot proxy / mapped feature) | `product:<lotId>` · `product:<lotId>:<featureId>` |
| Property set instance | `pset:<psetName>:<productKey>` |
| Relationship | `rel:<relType>:<parentKey>:<childKey>` |

Every `IfcRoot` gets a unique stable GUID; re-exports preserve identity for 4D links and TMR
re-submission diffing. GUID determinism versus golden values is a writer unit-test invariant (§4.4-1).

### 4.2 Geometry & coordinates

- Grade rules: **SUBMISSION** geometry comes from ingested surveyor data (12d/LandXML/CSV: points
  E/N/RL + strings; stored with datum realization, epoch, accuracy class, source-file SHA-256,
  surveyor identity → linked to the lot survey record). **DRAFT** geometry derives from
  `LotGeometry` (chainage/offset regenerated in grid coordinates from `ControlLine.points`; drawn
  WGS84 features transformed via the **existing `backend/src/lib/spatial/crs.ts` (proj4)** — no
  second projection implementation) and is labelled `GeometrySource=LotRecords (not survey)` in the
  manifest and `CIVOS_QA` pset.
- **SUBMISSION geometry mapping is explicit and closed.** Supported survey feature types map to
  defined IFC 2x3 representations: surveyed boundary strings → footprint whose vertices preserve
  each surveyed E/N/RL; surfaces bounded by top/bottom strings → solids whose thickness comes from
  the surveyed strings (a constant depth is **never invented** — the spike's constant-depth
  `IfcExtrudedAreaSolid` is DRAFT-only); AHD variation across a lot is never flattened. Vertical
  preservation tolerance defaults to the survey accuracy class recorded at ingestion (BEP-overridable),
  and the manifest states it. A survey feature outside the supported mapping set **hard-fails the
  SUBMISSION export for that lot** with a per-feature validation-report entry — never silently
  approximated. The exact mapping table (feature code → representation) is finalised in Phase 1b
  build against real 12d pickups.
- **One immutable project origin** (`IfcExportOrigin` on Project: E/N rounded to 100 m, set on first
  export, never changed): every file in a project shares it so multi-file federation overlays
  correctly. Grid offset carried machine-readably: `Project` pset `Datum`/`Zone` + manifest
  transform entry + `IfcSite.RefLatitude/RefLongitude/RefElevation` populated (WGS84 conversion via
  crs.ts). Elevations: AHD RLs from survey data in SUBMISSION grade; DRAFT grade emits Z=0 with an
  explicit `NoHeightData` marker.
- No-geometry lots are excluded from packages and listed in the validation report as not exportable.

### 4.3 Export surfaces, snapshots, packaging

- Aggregation is **BEP-configurable**: one-file-per-lot (default), per-discipline, or single
  project package — EIR does not prescribe per-lot files; the MPDT governs (§9.4).
- `POST /api/projects/:id/ifc-exports` creates an **immutable export snapshot**: generated files +
  `validation-report` + IDS results + model file register (EIR §9 p.24) + manifest (SHA-256 per
  file, source-record revision watermark, generator + validator versions, grade, origin, transform),
  persisted to the `documents` bucket via existing backend-mediated storage. Re-issues create a new
  snapshot with an explicit supersession link. `GET` endpoints list/download snapshots. A quick
  per-lot DRAFT download exists for preview but SUBMISSION artefacts are only ever snapshots.
- UI: lot detail action ("Export IFC — draft") + Handover Export page section ("As-constructed IFC
  package") with grade indicator and snapshot history. No new page.

### 4.4 Validation gate (layered — each layer catches what the previous cannot)

1. **Writer unit tests** — byte-level invariants: header, GUID alphabet + determinism versus golden
   values, STEP escaping order (`\` before `'`; `\X2\` for non-ASCII), `*`-vs-`$` derived slots,
   finite-number formatting, ring closure by reference.
2. **`ifcopenshell.simple_spf`** (STEP syntax) then **`ifcopenshell.validate --rules`** (schema +
   EXPRESS WHERE; requires `pytest` installed — undeclared dependency gotcha) in a
   `python:3.12-slim` CI step. Proven against the spike (Appendix B).
3. **buildingSMART `ifc-gherkin-rules`** (MIT, runs offline via `behave`) — implementer agreements
   incl. #CV-2x3-142 and GEM rules; this is the layer schema validation cannot see.
4. **IDS check (`ifctester`)** — the project IDS *is* the compiled form of the §9.2 "pre-determined
   schedule". **SUBMISSION grade is disabled per project until a project-approved TMR/BEP
   object-and-attribute schedule (classifications, object codes, value constraints, cardinalities —
   the D6 normative files + the project BEP) has been configured and compiled into the project
   IDS.** The four Guideline-derived psets are the floor the IDS always contains, not a substitute
   for the schedule; without an approved schedule, only DRAFT exports are possible and the UI says
   why. **Gotcha: `ifctester`'s CLI always exits 0 — use the Python API and assert
   `specification.status`.** The IDS + its results ship inside every SUBMISSION snapshot (this *is*
   the §9.2 deliverable).
5. **Round-trip semantic check** (web-ifc re-parse asserting names/psets/mesh) — proves intent, not
   validity; kept because it exercises the exact viewer engine. web-ifc performs **no** validation
   (proven: it happily parses files IfcOpenShell rejects).
6. **Manual, pre-first-client-delivery:** buildingSMART Validation Service run (IFC2X3 supported;
   API is auth-gated by emailed token; ToS re automation unverified — treat as manual) + import
   tests in the reviewer tools that matter (Navisworks/Revit/12d viewer) with a federation overlay
   of ≥2 lot files against a survey model.

### 4.5 Serializer production requirements (beyond the spike)

Typed STEP encoder (value objects, not string interpolation at call sites); ISO 10303-21 string
encoding incl. `\X2\` UTF-16BE escapes; reject non-finite numbers; polygon validation
(self-intersection, min-vertex, orientation normalisation — winding is convention CCW, no normative
rule exists); curved control-line densification; multi-product files; property-value length caps;
fixture corpus incl. a real surveyor pickup + hostile strings (`O'Brien Road`, unicode); fuzz tests
over the encoder. The spike (Appendix A) is the proof of approach, explicitly not the production
implementation.

## 5. Phase 2 — viewer

- Stack per §3 (ThatOpen), new lazy route `/projects/:id/models`; CI bundle assertion that the main
  bundle is unchanged.
- **Upload path is new infrastructure, not the existing document route** — that route is
  multer-in-memory with a 50 MB cap and would hold ~2× file size in RSS. Design: direct-to-storage
  resumable upload (Supabase TUS, which their docs recommend >6 MB) authorised by a short-lived
  backend-issued token, then server registration of the `Document` row; 200 MB initial cap;
  checksummed; Railway's request ceiling never sees the payload.
- **Conversion is asynchronous**: first-parse to `.frag` + properties JSON runs client-side on
  desktop (wasm) with results written back through a bounded endpoint, or in a worker for
  server-side conversion if the mobile gate demands it; cache keyed by (source SHA-256, parser
  version); only validated results are promoted. Phones prefer the pre-converted path.
- **Mobile gate is build item 0**: representative civil IFC on a mid-range Android, both paths,
  memory watched. No vendor publishes verified mobile IFC support; this is the phase's honest risk.
- In scope: orbit/pan/zoom, selection + §8.6-style pset tabs (our psets render as TMR describes —
  a nice demo moment), section plane, GlobalId/name search. Out: measurement, clash, multi-model
  federation.

## 6. Phase 3 — 4D

- **Reuses** `backend/src/routes/lots/statusTimeline.ts` (already shipped, already consumed by the
  map scrubber) — extended, not duplicated, with element-mapping awareness.
- **Prerequisite: `LotStatusEvent` ledger** — written in the same transaction as every status
  change (route-level, all callers), idempotent, `(lotId, status, at, byId, source)`. Historical
  backfill derived from AuditLog + dated fields is imported with `source='reconstructed'` and
  rendered as such (audit writes are best-effort today and not transactional — reconstructed
  history is honest, not exact).
- **Model identity:** `DesignModel` → immutable **`DesignModelVersion`** (source SHA-256, parser +
  cache versions, elementCount) → `ModelElement` unique on `(modelVersionId, ifcGuid)`; elements
  with missing/duplicate GUIDs quarantined at index time (authoring tools do emit both). Links
  attach to the *model* level with per-version resolution; a new version auto-remaps links by
  GlobalId match and reports orphans for manual re-link. Client-built element indexes are bounded
  and server-verified against the stored file before acceptance.
- Rendering: scrub slider → status-at-T per lot from the ledger → colour via the shared status
  token map → batched `highlightByID` per status bucket; unlinked elements ghosted; play =
  rAF-stepped T. Read-only.

## 8. Risks

1. **Mobile memory (P2)** — unverified industry-wide; gated by device spike; fallback moves
   conversion server-side (deployment change, not library change).
2. **TMR normative attribute files unpulled (P1b)** — D6 closes; Guideline tables are the interim
   basis and are explicitly non-comprehensive.
3. **LOD 500 interpretation** — "field-verified representation" satisfied by survey-derived prisms
   carrying accurate position/size + surveyor certification is our read; a TMR BIM reviewer could
   contest; confirm in the project BEP before first SUBMISSION delivery (1b acceptance item).
4. **Schema-valid ≠ conformant ≠ accepted** — layered gate (§4.4) narrows this; final acceptance
   evidence is reviewer-tool imports + first real submission; until then claims stay at
   "TMR-format, validated against schema + CV agreements + our IDS".
5. **Bundle creep (P2)** — ~1 MB gz lazy parser chunk; CI assertion in-phase.
6. **Library drift between now and trigger** — pin exact versions + re-run the license/health check
   at build trigger (the §3 table is a dated snapshot by design).
7. **CivilPro ships GA first** — acceptable; different tier, and our 1a is ~a week from trigger.

## Appendix A — proof-of-concept spike (throwaway; not repo code)

Zero-dependency Node STEP writer (~170 lines) emitting a 45-entity IFC 2x3 file for a fake lot
(LOT-042, subbase, CH1200–1300, 100 × 7.5 m footprint extruded 0.3 m, 12-property QA pset), plus a
web-ifc read-back verifier. Load-bearing details proven: IFC GUID base-64 encoding (digits-first
alphabet, first char 0–3), STEP escaping, `*` in derived `IfcSIUnit.Dimensions`, mandatory 2x3
`IfcOwnerHistory`, metre units per EIR §8.2, `ContextType='Model'`, polyline closed by reference,
site-origin offset with grid coordinates recorded.

Known, deliberate gaps vs Rev 2 (§4.1): single CIVOS pset instead of TMR's four (the content
correction that motivated Rev 2); no IfcBuilding/Storey (fails CV-2x3-142 despite passing schema
validation — the finding that motivated validation layer 3); random-v4 GUIDs (production: v5
domain-separated).

function ifcGuid() { /* 128 bits → 22 chars over IFC64; first char masked to 2 bits */ }
let nextId = 1; const lines = [];
function e(type, ...args) { const id = nextId++; lines.push(`#${id}=${type}(${args.join(',')});`); return `#${id}`; }
const S = (s) => `'${String(s).replace(/\\/g,'\\\\').replace(/'/g,"''")}'`;
const REAL = (x) => Number.isInteger(Number(x)) ? `${Number(x)}.` : String(x);

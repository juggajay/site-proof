## 1. Verdict

This window is **strong engineering shipped fast, and it holds up under adversarial reading.** The specs are unusually honest (the Wave D Rev 3 changelog documents its own line-number drift three times; the evidence docs disclose their own gaps), migrations are non-destructive with **machine-enforced drift checking** on every CI run, and the "proof-of-catch" tests are real — I mutated the D1a registry and three tests failed; a dedicated audit of 11 proof-of-catch claims found **zero vacuous tests**. The gates that carry money and quality — block-mode conform, `recordDecision` audit integrity, atomic single-send on chase digests — are genuinely enforced, not narrated, and a fabrication sweep of 9 public product claims found **all nine true** (the "don't fabricate product claims" class is clean for this window). Cross-company tenancy is clean: I verified the new spatial endpoints against the reference photo-path pattern and found no cross-tenant leak.

**What needs fixing before the next wave, in priority order (six Highs):** (1) offline retry **silently duplicates NCRs, diary events, and photos** when a mutation commits but the connection drops before the response — no idempotency key on four sync kinds, and it bites in exactly the low-signal field conditions the product targets; (2) a confirmed, blocking NSW test pack (`tfnsw-q6.v1`) shipped **without** the F1 alias rows for TfNSW method codes, so every NSW compaction test from the shipped NSW seed resolves to `null` and counts as zero — wrong number today in warn mode, an unclearable gate the day an NSW project turns on block mode; (3) the "one fact, one number" unification from #1625/#1630 is only half-done — NCR overdue age moved onto the shared `daysOverdue` helper, but hold-point age on the *same two dashboard responses* still uses `Math.ceil` from `createdAt`, printed under the **same `daysOverdue` key**, so one render line shows two rounding rules; (4) the Wave E automated chase **deletes a superintendent's live batch review-room tokens** because a `deleteMany` omits a `batchId: null` clause; (5) any CivilPro ITP with a **Milestone row is permanently un-importable** — the detection landed but the reviewer control to resolve it never did; (6) a subcontractor whose `testResults` portal toggle is **off** can still read located test data (own lots) through the new spatial-search endpoint, which enforces only the `lots` module. Below these: a Medium cluster where the new "My Work" surfaces dead-link every hold point (`/holdpoints` vs `/hold-points`) and are unreachable for the QM/PM roles they serve, and a route-vs-DB `CHECK`-constraint class that turns ordinary bad input into 500s.

**None of this blocks the program.** Wave D's #1666 is a faithful, well-tested implementation of the Rev 3 contract, and the remaining-phase risks (server-side PDF renderer in the API process, the AUD 12.00 cost ceiling, the 50 GB-vs-first-release-cap tension) are all ones the spec itself already names. **Verification:** type-checks clean on both packages; backend **5,540/5,541** DB-backed tests green (one local `ECONNRESET` infra flake, clean on isolated rerun); frontend **3,872/3,872** green; all migrations applied cleanly to the disposable test DB.

### HIGH

**H1 — Hold-point age is computed two different ways in one response, and printed under the NCR "overdue" key. CONFIRMED.**
`backend/src/routes/projects/projectOverviewRoute.ts:285` fills `daysOverdue` for NCR rows via the shared floor helper (`readiness/predicates.ts:375`), then `:290-292` fills the **same key** for hold-point rows with `Math.ceil((today - createdAt)/86400000)`. `frontend/src/components/dashboard/ProjectDashboard.tsx:256` renders both through one line, `{item.daysOverdue}d overdue`. `dashboard/statsRoute.ts:272` has the same `Math.ceil` on hold-point `daysStale`.
*Failure scenario:* a hold point created `2026-07-20T09:00Z`, viewed `2026-07-28T10:00Z` (8.04 days), prints **"9d overdue"** — rounded up, and against `createdAt`, which is not a due date; an NCR of the identical elapsed span prints "8 days overdue" beside it. This is exactly the "42 vs 41" off-by-one the `daysOverdue` docstring claims #1625 collapsed, still live on the hold-point limb. Companion (`F1b`): `systemAutomation.ts:306` reports stale hold points in `ceil`-ed **hours** in the alert email while `NeedsAttentionPage` floors the same span to days — "48 hours" in the email, "1 day overdue" on the chip. *Fix:* route the hold-point limb through `daysOverdue` and rename `projectOverviewRoute`'s hold-point key off `daysOverdue` (it is age, not overdue).

**H2 — A confirmed, blocking NSW test pack zero-counts every NSW compaction test, because D14.3 shipped the pack without the F1 aliases. CONFIRMED.**
`backend/src/lib/readiness/sufficiency/testCategories.ts:55-102` (the alias table) carries VIC/QLD/TMR strings (`tmr q141a/b`, `as 1289.5.4.1`, `rc 316.00`, `section 173`) but **no TfNSW method codes** (T173/T166/T162). Its own scope note (`:50-53`) says aliases ship only for strings a lot under a *resolved* pack can carry, and names `vicroads-204.v1` as "the only resolved pack" — true at F1 (#1598). Then `tfnsw-q6.v1` (#1615) shipped `status: 'confirmed'` (`rulesets/tfnsw-q6.v1.ts:408`) and no alias followed. The shipped NSW seeds emit exactly the failing strings — `seed-itp-templates-nsw.js:267` `testType: 'T173 (Nuclear) / T166 / T162'`, `seed-itp-templates-nsw-pavements.js:175,184` `'T173'`. Tokenising any of them (`testCategories.ts:177-196`) yields tokens absent from `ALIAS_LOOKUP` and `LAB_REFERENCE_TOKENS`, so `classifyTestType` returns `null` → `candidateCategories` `[]` → `testAttributesToRule` false for every test.
*Failure scenario:* NSW/TfNSW project, `pavement_unbound` lot, 800 m² polygon, four verified passing T173 tests. `PAVEMENT_COMPACTION_DENSITY` is scale-independent, so nothing rescues it into `unknown`; `bandedCount` requires 4, `passingCount` is 0, verdict `insufficient`. In warn mode the panel shows "4 compaction tests … 0 verified conforming" — a wrong number on a real lot. In **block mode** (`sufficiencyBlocks` true, `evaluate.ts:499-502`) nobody below owner/admin can conform the lot, and no amount of correct testing clears it. Why nothing caught it: the seed sweep test is scoped `VIC_MODULES = /^seed-itp-templates-vic-.*\.js$/` (`testCategoriesSeedSweep.test.ts:73`) despite its own header saying D14.3 would add NSW rows; and `characterization/seedCorpus.ts:198-200` still asserts "the main corpus project … resolves NO ruleset", stale since #1615. **This is a High not a Critical only because default mode is `warn`.** *Fix:* add the TfNSW method-code aliases and an NSW row to the seed sweep — a data change, not an engine change.

**H3 — The automated chase digest deletes a superintendent's live batch review-room tokens. CONFIRMED.**
`backend/src/routes/holdpoints/chaseCore.ts:216-226` (`revokeSupersededChaseReleaseTokens`) issues a `deleteMany` on `{holdPointId, recipientEmail, usedAt: null, token != fresh}` with **no `batchId` exclusion**. Batch review-room tokens are created carrying `batchId` (`requestReleaseRoutes.ts:417`) with `recipientEmail` equal to the address written into `HoldPoint.notificationSentTo`. The E2 digest (`holdPointChaseAutomationGroup.ts:111-120`) resolves that same address, mints a fresh batch-less token, and on a successful send calls the revoker (`:207`) — exact email match, `usedAt` null, differing hash → the batch token row is deleted. Every public batch route reaches hold points through `batch.releaseTokens` (`publicBatchRoutes.ts:47-58`).
*Failure scenario:* a superintendent is emailed a review room covering eight hold points; the hourly chase fires on three; the room now lists five, and `GET /public/batch/:token/holdpoints/:id` returns 404 for the other three. They can still release via the new per-item digest links, so it is degradation not lockout — but it **silently rewrites an external evidence artefact** and the released set no longer matches the batch that was sent. E2 industrialises this hourly across every canary project. *Fix:* one clause — `batchId: null` in the `deleteMany` where.

**H4 — Spatial-search serves test results to a subcontractor whose `testResults` portal module is switched off. CONFIRMED.**

**H5 — Offline retry silently duplicates field records on four mutation kinds; no idempotency key. CONFIRMED.**
`frontend/src/lib/offline/syncWorker.ts:780-791` POSTs `ncr_create` with `{projectId, description, category, lotIds}` — the client's own `ncrId` is destructured (`:778`) but **deliberately not sent** — and `backend/src/routes/ncrs/ncrCore.ts:245-247` does a bare `tx.nCR.create` with no dedupe. `authFetch` has no client timeout (`lib/api.ts`), so when a request lands and the server commits but the connection drops before the 201, `authFetch` throws, `runSyncStep`'s catch marks the item errored and leaves it queued, and the 60s auto-retry creates a second record. Same shape on `delivery_save`, `event_save`, and `photo_upload` (the photo path has a re-upload guard but it's written *after* `await response.json()`, so it can never fire in the one case that matters).
*Failure scenario:* a foreman raises a defect on one bar of signal; `POST` commits NCR-0042; the radio drops before the 201; the queue retries at the top of the hill → NCR-0043, identical text, same lot, a second round of client notifications (`ncrCore.ts:342-425`). This corrupts the quality record silently, in exactly the low-signal field conditions the product is built for. Not Critical only because it's conditional on partition timing and the duplicate is visible as two numbered NCRs. Verified idempotent and *not* at risk: `itp_completion` (find-or-create), `diary_save/submit` (upsert + content dedupe), `lot_edit` (PATCH), `docket_*` (sync disabled). *Fix:* client-generated idempotency key echoed to the four backend routes.

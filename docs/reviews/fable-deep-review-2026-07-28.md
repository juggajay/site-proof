### HIGH

**H1 — Hold-point age is computed two different ways in one response, and printed under the NCR "overdue" key. CONFIRMED.**
`backend/src/routes/projects/projectOverviewRoute.ts:285` fills `daysOverdue` for NCR rows via the shared floor helper (`readiness/predicates.ts:375`), then `:290-292` fills the **same key** for hold-point rows with `Math.ceil((today - createdAt)/86400000)`. `frontend/src/components/dashboard/ProjectDashboard.tsx:256` renders both through one line, `{item.daysOverdue}d overdue`. `dashboard/statsRoute.ts:272` has the same `Math.ceil` on hold-point `daysStale`.
*Failure scenario:* a hold point created `2026-07-20T09:00Z`, viewed `2026-07-28T10:00Z` (8.04 days), prints **"9d overdue"** — rounded up, and against `createdAt`, which is not a due date; an NCR of the identical elapsed span prints "8 days overdue" beside it. This is exactly the "42 vs 41" off-by-one the `daysOverdue` docstring claims #1625 collapsed, still live on the hold-point limb. Companion (`F1b`): `systemAutomation.ts:306` reports stale hold points in `ceil`-ed **hours** in the alert email while `NeedsAttentionPage` floors the same span to days — "48 hours" in the email, "1 day overdue" on the chip. *Fix:* route the hold-point limb through `daysOverdue` and rename `projectOverviewRoute`'s hold-point key off `daysOverdue` (it is age, not overdue).

**H2 — A confirmed, blocking NSW test pack zero-counts every NSW compaction test, because D14.3 shipped the pack without the F1 aliases. CONFIRMED.**
`backend/src/lib/readiness/sufficiency/testCategories.ts:55-102` (the alias table) carries VIC/QLD/TMR strings (`tmr q141a/b`, `as 1289.5.4.1`, `rc 316.00`, `section 173`) but **no TfNSW method codes** (T173/T166/T162). Its own scope note (`:50-53`) says aliases ship only for strings a lot under a *resolved* pack can carry, and names `vicroads-204.v1` as "the only resolved pack" — true at F1 (#1598). Then `tfnsw-q6.v1` (#1615) shipped `status: 'confirmed'` (`rulesets/tfnsw-q6.v1.ts:408`) and no alias followed. The shipped NSW seeds emit exactly the failing strings — `seed-itp-templates-nsw.js:267` `testType: 'T173 (Nuclear) / T166 / T162'`, `seed-itp-templates-nsw-pavements.js:175,184` `'T173'`. Tokenising any of them (`testCategories.ts:177-196`) yields tokens absent from `ALIAS_LOOKUP` and `LAB_REFERENCE_TOKENS`, so `classifyTestType` returns `null` → `candidateCategories` `[]` → `testAttributesToRule` false for every test.
*Failure scenario:* NSW/TfNSW project, `pavement_unbound` lot, 800 m² polygon, four verified passing T173 tests. `PAVEMENT_COMPACTION_DENSITY` is scale-independent, so nothing rescues it into `unknown`; `bandedCount` requires 4, `passingCount` is 0, verdict `insufficient`. In warn mode the panel shows "4 compaction tests … 0 verified conforming" — a wrong number on a real lot. In **block mode** (`sufficiencyBlocks` true, `evaluate.ts:499-502`) nobody below owner/admin can conform the lot, and no amount of correct testing clears it. Why nothing caught it: the seed sweep test is scoped `VIC_MODULES = /^seed-itp-templates-vic-.*\.js$/` (`testCategoriesSeedSweep.test.ts:73`) despite its own header saying D14.3 would add NSW rows; and `characterization/seedCorpus.ts:198-200` still asserts "the main corpus project … resolves NO ruleset", stale since #1615. **This is a High not a Critical only because default mode is `warn`.** *Fix:* add the TfNSW method-code aliases and an NSW row to the seed sweep — a data change, not an engine change.

**H3 — The automated chase digest deletes a superintendent's live batch review-room tokens. CONFIRMED.**
`backend/src/routes/holdpoints/chaseCore.ts:216-226` (`revokeSupersededChaseReleaseTokens`) issues a `deleteMany` on `{holdPointId, recipientEmail, usedAt: null, token != fresh}` with **no `batchId` exclusion**. Batch review-room tokens are created carrying `batchId` (`requestReleaseRoutes.ts:417`) with `recipientEmail` equal to the address written into `HoldPoint.notificationSentTo`. The E2 digest (`holdPointChaseAutomationGroup.ts:111-120`) resolves that same address, mints a fresh batch-less token, and on a successful send calls the revoker (`:207`) — exact email match, `usedAt` null, differing hash → the batch token row is deleted. Every public batch route reaches hold points through `batch.releaseTokens` (`publicBatchRoutes.ts:47-58`).
*Failure scenario:* a superintendent is emailed a review room covering eight hold points; the hourly chase fires on three; the room now lists five, and `GET /public/batch/:token/holdpoints/:id` returns 404 for the other three. They can still release via the new per-item digest links, so it is degradation not lockout — but it **silently rewrites an external evidence artefact** and the released set no longer matches the batch that was sent. E2 industrialises this hourly across every canary project. *Fix:* one clause — `batchId: null` in the `deleteMany` where.

**H4 — Spatial-search serves test results to a subcontractor whose `testResults` portal module is switched off. CONFIRMED.**
`backend/src/routes/spatialSearch.ts:86` calls `requireSubcontractorLotPortalModules(user, projectId)` with no module list, which defaults to `['lots']` only (`lots/access.ts:25-40`). No test covers it: `spatialSearch.test.ts:95` seeds `portalAccess: { lots: true }`, which merges over defaults that leave `testResults` true. *Fix:* `requireSubcontractorLotPortalModules(user, projectId, ['testResults','documents'])`, or gate per-collection so a lots-only subbie still gets lots.

## 4. Wave D drift & remaining-phase risks

**#1666 (D1a-respec) vs Rev 3 §4.1 — faithful.** I read the spec §4.1 and the full #1666 diff, then mutation-tested it. Every clause landed: `HANDOVER_BLOCKING_REASON_CODES` is a runtime `as const` subset of the shipped `READINESS_REASON_CODES` (`reasonCodes.ts:116-136`), not a second vocabulary; `HandoverReasonCode` derives from it, replacing the hand-listed `Extract<>` (`futureConsumers.ts:113`); `EvidenceReadinessItem.code` narrows `string → ReadinessReasonCode` (`core.ts:22-30`); `blockingItem()` is the one typed constructor with byte-order preserved for the characterization snapshots (`core.ts:271-293`); `LotCloseoutReadinessSnapshot` + `CloseoutReadinessResponse` define D1a's batched input with the `unplacedLots`/`unclassifiedLots` escapes. **Mutation check:** removing `insufficient_test_count` from the registry failed AT-138(b), AT-138(d) and the derived-union test (3 failures) — the "mutation-verified" claim in the PR body is real.

**Drift items (all minor; the implementation is the correct call where it diverges):**

1. **Spec §14 AT-138(b)/AT-119 say the registry "equals" the emitted hard-blocker set; the shipped test asserts classification + membership, not equality — and that is correct.** Two registry codes (`open_major_ncrs`, `unreleased_hold_points`) are emitted with `blocksAction: false` on their advisory surfaces, so the registry is a curated *superset* of the emitted-hard-blocker set on those two. The code documents this precisely (`reasonCodes.ts:127-135`) and AT-138(b) uses "membership-of-emitted, never emitted-equals-set". The spec's "equals" phrasing in a couple of §14 rows is looser than what shipped; the §4.1.1 caveat governs. No code change needed — flag it so a later reviewer doesn't "fix" the test toward the spec's word and break it.

2. **AT-138(b) catches registry-vs-battery drift, not emitter-vs-battery drift (test-honesty finding, confirmed).** The battery (`emitBatteryItems()`) is a hand-maintained set of fixture inputs. A *new* hard-blocker branch added to an emitter without a matching battery input is invisible to AT-138 — the exact drift the contract exists to prevent, one indirection out. Worth a comment on `emitBatteryItems` that a new blocking emitter needs a battery row, or a coverage assertion that every emitter file is represented.

3. **`REASON_CODE_PROVENANCE.open_major_ncrs` still names the superseded predicate `ncrSeriousIncludingCritical` (`reasonCodes.ts:230-233`)** while #1666's own snapshot comment records the shipped emitter now uses `ncrSerious` (severity `major`) after the F0.2b unification. Harmless on real data (`critical` is not a schema severity), self-documented — but the provenance registry, whose whole job is to be authoritative, is one edit stale.

4. **D1a-respec is types+tests only, as specified — so nothing populates these types in production yet.** `LotCloseoutReadinessSnapshot`/`CloseoutReadinessResponse` exist with no consumer; the `GET /closeout-readiness` endpoint (D1a proper) is the next phase. Expected, but worth stating plainly: the contract is in place, the surface is not.

**Rev 3 ambiguities / risks that will bite the remaining phases (D1b.0 → D1d):**

- **The exit gate is not yet fixed.** §15 item 4 and §4.5.3 leave the archive cap — and therefore the 50 GB-vs-first-release-cap exit criterion — to be *decided by* the `D1c.0` spike. The spec is honest that "50 GB reference dataset and a 5 GB first-release cap are mutually exclusive", but it means D's definition-of-done is itself a spike output. Sequence D1c.0 early; it gates the exit gate's own wording.
- **The AUD 12.00 cost ceiling (§4.5.6 / J8) is a pre-declared hard commercial commitment nobody has validated.** Declaring it before measuring is the right discipline (it *can* fail), but it is Jay's number to hold, and if D1c.0 measures above it the responses (lower cap / cheaper path / priced add-on) are all commercial decisions, not engineering ones. This is correctly a Jay decision — flag that it blocks D1c.2 config, not just D1c.0.
- **Server-side PDF rendering in the API process is the biggest architectural bet in D** (§4.3.1, `[DH-i]`). It buys a genuine security simplification (no client bytes, no upload route, no derivation check — the doctored-bytes class is closed structurally, which is the right trade) at the cost of a new backend PDF dependency and a CPU/memory-bound workload in the process that serves every request. §18.3 item 8 already flags this; the §4.3.6 RSS (<96 MiB) and wall-clock (<1.5 s p95) thresholds are load-bearing and the threat model must cover renderer resource exhaustion. Watch p95 on unrelated endpoints during folio issuance in D1b — that is the number that would say "this belongs in the worker after all".
- **AT-124's contract is stricter than "ignore".** A client-supplied `sha256`/`compiledFrom` must be *rejected outright*, not merely ignored. Easy to accidentally build the ignore version; make sure the D1b route 400s on their presence.
- **The `[DR2-B1]` gaps that pushed D1d from XS to S are real and verified** — `ALLOWED_DOCUMENT_MIME_TYPES` has no video type and multer caps at 50 MB, so CCTV genuinely cannot be uploaded today. D1d's separately-governed video allow-set + size ceiling is the correct scope; just note it interacts with §4.5.3's admission cap (a project of CCTV runs is exactly the shape that hits it).

Net: the Rev 3 spec is one of the most rigorous in the repo and #1666 is a clean first phase. The residual risk is not correctness of the contract but that **three of D's hardest decisions (cap, cost, renderer placement) are deferred to spikes that haven't run** — which the spec says out loud, so the risk is schedule/scope, not a hidden defect.
